# 开发者日志

一篇日志只讲**一件**已经发生的事，讲清它怎么错的、怎么改对的。不是功能清单，不是进度汇报，不是给读者的项目介绍。

读者是三个月后的自己，以及评审。他们不需要知道有什么节点，需要知道当时卡在哪、判断错在哪一步。

## 六段骨架

顺序不许调，段 1 不许变成背景介绍。

1. **我要的** — 三句以内。只写要达到的观感或结果，不写为什么做这个项目。写完立刻自查：删掉第一句还能不能成立，能就删。
2. **第一版什么样、错在哪** — 写**现象**，写你看到什么、量到什么，不贴代码、不讲实现结构。"满屏雪花"是现象，"雾的采样频率不对"不是。
3. **为什么会错** — 拆到能讲清**一层**原理为止，比如"零均值信号在任意一帧的均值都是透明的，所以它挡不住任何东西"。这里要简短交代**原始规格/史料说了什么**，只留直接影响这次判断的那几条；再写你照它读错了哪一句，或者它本来就没规定的那个空隙在哪里。规格往往没错，错在你把没规定的地方补成了某个默认值。
4. **怎么改的** — 说取舍、说代价：砍掉了什么，换来了什么，代价具体落在哪个数值或哪个观感上。不许列清单，不许写成"1. 2. 3."。做不到的要求要在这里认下来，写清差多少、为什么没做到。
5. **还不满意的** — 留**一个**真实存在的问题。它必须是你现在答不上来的，不许圆。判据：你能不能说出下一步为什么难；说不出来就是假的。
6. **一句话收尾** — 只陈述事实或结论。不升华、不表态、不展望。

全文 900–1400 字，宁可短。

## 取材规则

素材只从这四处挖，不发明：

- `git log --oneline` — 一次提交就是一次判断，提交信息里的措辞往往已经含了当时以为的因果。
- `TASKS.md` 的「工作留痕」 — 每条都带"卡在哪"，那半句通常是段 5 的真源头。
- 对话里真实的失败 — 用户说的原话（"与其说是雾不如说是灰尘"）比自己的复述好用，也更容易定位到具体哪一步判断错了。**今天错了两次就写两次**，不要合并成一次"经过迭代"。
- 改动前后的截图 — 能拿到数值就写数值（对比 14.5/255 与 5.8/255），拿不到就写现象。截图本身不必进仓库，但结论要能被数字支撑。
- 配图位置 — 第一版的图紧跟在段 2 写现象的那句后面，不要攒到最后。成果对比图放在它**最能证伪自己**的地方，通常就是段 5：一张图同时显示"成了"和"还不行"，比放在段 4 报喜有用。图里看得出的事实必须和正文对得上，对不上就先改正文——静态截图常常看不出"在动"这件事，这种落差要写进去。
- 施工令/规格文档里被推翻的那一版 — 只取直接影响本次判断的条款，用来交代"我当时依据的是什么"。

## 写法禁令

1. 不写"接下来我打算…"这类进度汇报。
2. 不贴大段代码，最多引用一行。
3. 不用"首先/其次/最后""总的来说""值得注意的是""不难发现"，也不写"真正的问题是""代价很具体""还有一处我没做到"这类报幕句——直接说事，别先报一句幕再说。
4. 不用四字词堆砌，不写"效果拔群""相得益彰""淋漓尽致"。
5. 不假装顺利。错了几次写几次，并指明错在哪一步的判断上，不是"走了些弯路"。
6. 结尾不升华、不表态、不展望。"这个项目一定会…"一律删掉。也不写成能被单独摘出来的金句：不用对偶、不用警句、不留"这两件事根本不是一件事"这种腔调，收尾用事实。
7. 不要每段开头都来一句总结句。

## 自检清单

1. 段 2 有没有出现代码、架构名词或者"我加了 X 节点"？段 3 有没有把原理讲到能反驳自己？
2. 全文搜一遍"接下来""总的来说""最后"，以及任何一句表态或展望；有就删。
3. 段 5 那个问题，我能不能说出它为什么难？说不出，说明它是凑数的，换一个。
